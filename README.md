deterioration.

## Problem statement

Millions of people living with Type 2 diabetes are monitored through periodic
laboratory HbA1c tests, typically every 3–6 months. Between those visits,
clinicians have no practical way to see how a patient's daily activity, sleep,
and heart-rate behaviour relate to their glycaemic trajectory. Wearable
devices generate exactly this behavioural data, but it lives in a different
world from the clinical record:

- **Clinical data** (HbA1c, fasting glucose, BMI, diagnosis history) is
  accurate but sparse in time.
- **Wearable-like data** (steps, active minutes, resting heart rate, sleep) is
  dense in time but says nothing directly about glycaemia.

Clinicians therefore lack a single, explorable view that combines both — and
lack a safe, transparent way to ask *"what might this patient's next HbA1c
look like under a different lifestyle pattern?"* without over-claiming.

### Healthcare use case

GlycoTwin is a **clinician-facing decision-support demonstration** in which a
reviewer can:

1. Select a synthetic patient and review their **historical clinical record**
   (HbA1c, fasting glucose, BMI) with the **date of the last laboratory
   result**.
2. Inspect **longitudinal wearable-like trends** (14-day windows of steps,
   active minutes, resting heart rate, sleep duration and consistency).
3. Request a **model-estimated future HbA1c** generated by a real, saved
   regression pipeline, with an exact, per-feature explanation of how the
   model produced its number.
4. Run **exploratory what-if scenarios** — change supported lifestyle inputs
   and compare baseline versus scenario estimates.
5. Review **configurable follow-up alerts** that flag synthetic records
   against a documented, non-clinical demo rule, prompting *consider
   clinical/laboratory review*.

**Intended outcome:** a transparent, runnable decision-support concept that
shows how historical clinical and dynamic wearable data can be unified for
diabetes monitoring — while stating, at every screen, that predictions are not
laboratory results and never replace clinical judgement.

**Explicitly out of scope:** diagnosis, treatment or medication guidance,
deterioration-risk probabilities (no validated future-event label exists),
real device ingestion, and any real booking/clinic integration.

### AI/ML model details

- **Task:** regression — estimate a synthetic future HbA1c value 90 days after
  a documented prediction timestamp from historical clinical features plus a
  preceding 14-day wearable window.
- **Model family:** two deterministic scikit-learn candidates —
  **clinical-only Ridge baseline** vs **clinical-plus-wearable Ridge** — both
  fitted on the training split only and selected by validation MAE. The test
  split is patient-disjoint and held out from fitting and selection.
- **Measured results (synthetic data only):**

  | Candidate | Validation MAE | Held-out test MAE | Held-out test RMSE |
  | --- | ---: | ---: | ---: |
  | Clinical-only Ridge | 0.231 | 0.149 | 0.174 |
  | Clinical-plus-wearable Ridge | 0.206 | 0.142 | 0.159 |

- **Explainability:** each `/predict` response includes exact linear feature
  contributions (`coefficient × scaled value` + intercept) that reconstruct the
  estimate exactly — verified by an automated test. SHAP was evaluated and
  deliberately not used; for a linear model SHAP's `LinearExplainer` yields the
  same attributions (rationale in the [model card](docs/model_card.md)).
- **Honesty boundaries:** no uncertainty quantification, no deterioration-risk
  classifier (no valid future-event label exists), and synthetic evaluation
  does **not** establish clinical performance.

## How the system works

```text
Versioned synthetic-data generator (seed 20261012, 40 patients)
        │  patients · clinical observations · wearable days · future target
        ▼
Validation + leakage-safe feature pipeline (patient-disjoint 70/15/15 split)
        ▼
Synthetic HbA1c Ridge benchmark + saved preprocessing artifact
        ▼
FastAPI service (/health /patients /predict /simulate /alerts)
        ▼
React/TypeScript clinician dashboard (localhost:5173 via /api proxy)
```

## Setup

Use Python 3.11 through 3.14. In this environment, use `python3`; do not use
the unrelated system `pip` executable.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
```

## Checks


## Generate and prepare synthetic data

The committed sample is generated from a fixed seed. Regenerate it and create
local processed splits with:

```bash
PYTHONPATH=src python -m glycotwin.data.generate \
  --output-dir data/sample --patient-count 40 --seed 20261012
PYTHONPATH=src python -m glycotwin.data.prepare \
  --input-dir data/sample --output-dir data/processed --seed 20261012
```

The preparer validates schemas, missing values, duplicate patient/date rows,
date fields, patient linkage, target ordering, and documented plausible ranges.
It selects the latest clinical observation at or before prediction time, exactly
14 wearable days ending at prediction time, and then writes patient-disjoint
70%/15%/15% train/validation/test splits. Generated targets and processed data
are synthetic only; the target is not a laboratory result.

## Train the synthetic benchmark

```bash
PYTHONPATH=src python -m glycotwin.training.train \
  --processed-dir data/processed --model-dir models
```

This compares clinical-only and clinical-plus-wearable Ridge-regression
pipelines, selects the lower validation-MAE candidate, evaluates it on the
patient-disjoint held-out test split, and saves an artifact containing both the
scaler and model. Results are synthetic-only and do not establish clinical
accuracy. See the [model card](docs/model_card.md) for measured results and
limitations.

## Run the local API

After training the artifact:

```bash
PYTHONPATH=src uvicorn glycotwin.api.main:app --reload
```

Use `http://127.0.0.1:8000/docs` to inspect and call the synthetic-only API.
It provides health, patient browsing, real-pipeline prediction (with exact
linear feature contributions), exploratory simulation, and a configurable
non-clinical follow-up rule. See the [API contract](docs/api.md) for
request/response details.

## Run the dashboard

Start the API (previous section), then in a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The dev server proxies `/api` to the backend on
port 8000. The dashboard shows synthetic patient selection, historical
clinical/laboratory summaries with the last lab date, wearable-like trend
charts, model estimates with the exact linear explanation, a what-if scenario
simulator, and the configurable follow-up alert panel. Every view states that
the system is a synthetic research/demo prototype, not a diagnosis.

For a production-style bundle, run `npm run build` inside `frontend/` and
serve `frontend/dist/` behind the same `/api` proxy.

Troubleshooting: recent npm versions restrict install scripts. If `npm run
build` fails with an esbuild error, approve the skipped script once with
`npm install-scripts approve esbuild` (inside `frontend/`) and re-run.

## Limitations and responsible use

- All data is **synthetic and project-generated**; it cannot support clinical,
  causal, prevalence, or real-world risk claims.
- The model target is produced by a documented generator formula, so results
  demonstrate pipeline behaviour on synthetic relationships only.
- The model was evaluated on six held-out synthetic patients and does not
  quantify uncertainty.
- The follow-up alert threshold is a **configurable demo rule**, not clinically
  approved guidance.
- The prototype is a research/demo decision-support concept — **not a medical
  device**, not a diagnosis, and not a substitute for clinician judgement or
  laboratory testing.
